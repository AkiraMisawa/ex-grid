# グリッドはデータを引かない。Consumer が窓を押し込む

グリッドは行のコレクションも、行を取ってくる関数も受け取らない。**いま表示すべき Window**
をパラメータとして受け取り、それが足りないときに「この範囲が要る」と**通知するだけ**にする。
表示が変わるのは、Consumer が新しい Window を渡したとき。

ソート状態・フィルタ状態・読み込み中かどうかも、すべて Consumer が所有してグリッドに渡す。
**グリッドはソートもフィルタも実行しない。**

入口は 2 つ。対等ではなく、**引く形が押す形の上に載る単方向の関係**にする。

```razor
@* 押す形 — 素の入口 *@
<ExGrid Window="@State.Value.Window" TotalCount="@State.Value.Total"
          Sorts="@State.Value.Sorts"   Filter="@State.Value.Filter"
          IsLoading="@State.Value.IsLoading"
          OnRangeNeeded="r => Dispatcher.Dispatch(new RangeNeeded(r))"
          OnSortChanged="s => Dispatcher.Dispatch(new SortChanged(s))"
          OnEditsCommitted="e => Dispatcher.Dispatch(new EditsCommitted(e.Edits))" />

@* 引く形 — 同梱の便利層。内部で押す形を駆動しているだけ *@
<ExGrid Source="GridSource.From(_rows)" />        @* 手元に全部ある *@
<ExGrid Source="GridSource.Fetch(FetchAsync)" />  @* サーバページング *@
```

## 改訂の経緯

当初この ADR は「非同期の Data Source（関数）を受け取る」= **引く形**だった。決定の核心
（コレクションを受け取らない／サーバ側にソート・フィルタを委譲できる形を最初から用意する）
は変わっていないが、**向きを反転した**。理由は、後から編集機能を入れると決めたあとに
出てきた。

1. **上書きされた列のソートが、引く形では静かに壊れる。** 編集はベースへの疎な差分
   （[ADR-0007](./0007-edits-are-an-overlay-owned-by-the-consumer.md)）なので、サーバは
   それを知らない。引く形ではグリッドがソート状態を持ち `Query` に載せて投げるため、
   **返ってきた並びが正しいかどうかグリッドには判別できない**。押す形ではグリッドが
   ソートを実行しないので、誤った並びを出しようがない。
2. **キャッシュの無効化が、問題として発生しなくなる。** 引く形ではグリッドが窓を
   キャッシュするため、シナリオが変わったら捨てさせる仕組み（世代トークン）が要る。
   押す形ではグリッドがキャッシュを持たないので、捨てる必要もない。
3. **View State / Saved View が副産物になる。** 列幅・列順・ソート順・フィルタ条件を
   シリアライズして永続化する要件（`CONTEXT.md` の **View State**）に対し、引く形では
   「グリッド内部の状態を外に出し、復元時に押し戻す」双方向バインディングが必要になる。
   押す形では状態が最初から外にあるので、保存も復元も State の出し入れで済む。
4. **状態管理ライブラリと噛み合う。** Fluxor をはじめ Flux 系はすべて押す形。押す形を
   本来にしておけば変換層が要らない。

## Considered Options

- **行のコレクションを同期で受け取る** — 却下（当初から）。書き味は最も楽でソートも
  フィルタも同期で単純になるが、サーバ側データ操作が必要になった時点で作り直しになる。
- **引く形（非同期関数）を本来とする** — 却下。**破綻はしない** — MudBlazor の
  `MudDataGrid` が `Items` / `ServerData` でこの形を採り、広く使われている実績がある。
  却下の理由は上記 1〜4 であって、引く形が動かないからではない。編集機能を持たない
  グリッドなら引く形で十分。
- **引く形と押す形を対等な公開 API にする** — 却下。2 つの実装を保守することになり、
  合計行の出し方や全選択の意味が API ごとに食い違う。今回の 2 入口は**対等ではなく**、
  `Source` は内部で押す形を駆動する薄い層であり、振る舞いの経路は 1 本しかない。

## Consequences

- **Consumer の負担が増える。** 窓の保持、範囲要求への応答、読み込み中の表現を自分で
  書くことになる。**同梱の `GridSource`** がこれを肩代わりするので、小さな Consumer の
  書き味は引く形と変わらない（`<ExGrid Source="GridSource.From(_rows)" />`）。
- **同梱の in-memory 実装は「参照実装」であり、その意味論は仕様である。** `GridSource.From`
  はフィルタとソートを実際に実行する — つまり「contains は大文字小文字を区別するか」
  「null はソートの先頭か末尾か」といった**意味を決めている**。サーバ側実装はこれと
  同じ意味になるように書かれなければならない。
  [ADR-0002](./0002-filters-are-a-serializable-model-not-linq-expressions.md) が
  「演算子の集合が公開 API になる」と書いたが、演算子だけでは足りず意味も仕様に含まれる。
- **`IsLoading` を渡し忘れると静かに壊れる。** ユーザがフィルタを変えたのに新しい Window が
  まだ届いていない間、グリッドは「古い結果」を何事もなかったように表示し続ける。引く形なら
  グリッドが自分の未完了リクエストを知っていた。
- **スクロールの追従性が Consumer の実装品質に依存する。** 先読み・高速スクロール中の
  リクエスト間引き・古いリクエストの破棄は、押す形では Consumer 側（または `GridSource`）の
  責任になる。
- **編集の反映はグリッドの責任ではない。** グリッドは渡された Window を描くだけで、
  Overlay を自分で適用しない。編集が画面に出るまでの条件は
  [ADR-0007](./0007-edits-are-an-overlay-owned-by-the-consumer.md)「編集が画面に出るまでの
  3 つの環」を参照。
- **クリップボードにコピーできる範囲に上限が要る。** グリッドが手元に持つのは現在の
  Window だけなので、選択範囲がそれを超えると自力ではコピーできない。上限を超えたときの
  挙動は [ADR-0005](./0005-copy-refuses-rather-than-truncates.md)。
- **ページ間の不整合は `poke` では起きない。** ベースラインは content-addressed で
  フィード版がスタンプされた不変のスナップショット（poke ADR-0001 / ADR-0008）なので、
  問い合わせをフィード版にピン留めすればページングは常に整合する。リアルタイムに流れ
  続けるデータを扱う Consumer では、この前提は成り立たない。
