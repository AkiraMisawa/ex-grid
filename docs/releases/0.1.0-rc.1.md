# 0.1.0-rc.1

Published: pending
Packages: ExGrid, ExGrid.MudBlazor, ExSheet.Engine, ExSheet, ExSheet.MudBlazor, ExGrid.Data, ExGrid.Data.Arrow, ExPivot.Engine, ExPivot, ExPivot.MudBlazor
Target: net10.0

## Highlights

- The first version offered for a stable release: the whole family at one version, checked against the Definition of Done, with ExGrid on Blazor Server as well as WebAssembly ([Getting started](getting-started#requirements); ADR-0200, ADR-0205).
- Live data held by Row Key: the bundled sources take a Change Batch whole, and a write lands as the user entered it, on the row it was aimed at ([Live updates and the Change Highlight](exgrid/data#live-updates-and-the-change-highlight); ADR-0068).
- Excel's status-bar figures over the selection, in ExGrid, ExSheet and ExPivot, and Excel's Heading Mark on the selected columns and rows ([Status-bar figures](exgrid/selection#status-bar-figures)).
- What was copied stays outlined while the clipboard holds it, as Excel's moving border does ([Copy](exgrid/clipboard#copy); ADR-0170).
- ExPivot reports a server computes, sending only the Windows the reader sees ([A server's source](expivot/sources#a-server-s-source)).

## Breaking changes

- **ExGrid:** A change of the row order no longer discards an open edit, and `EditDiscardReason.OrderChanged` is gone. With a Row Key the editor moves with its row; without one, Enter is refused through the new `OnCommitRefused` as `OrderMoved`, and the typing is kept. Code that handled `OrderChanged` in `OnEditDiscarded` handles `OnCommitRefused` instead ([Editable columns and the Edit Intent](exgrid/editing#editable-columns-and-the-edit-intent); ADR-0142, #70).
- **ExGrid:** `--ex-state-modified-mark` is now a colour, the colour of a triangle in a Modified cell's top right corner, where it was a whole `box-shadow`. A stylesheet that set it to a shadow sets it to a colour ([Visual Tokens](exgrid/appearance#visual-tokens); ADR-0029, #68).
- **ExGrid:** `ExGrid.MudBlazor` takes MudBlazor `[9.6.0,10.0.0)` where it took 9.0.0 or anything above it: an application that references MudBlazor 9.0 to 9.5 moves it to 9.6.0 or a later 9.x, or restore stops it (NU1605, an error by default), because below 9.6.0 the filter panel's operator has no role and no name where the keyboard is, and from 9.3.0 to 9.5.0 a refused filter value loses its words. An application on MudBlazor 10 is warned at restore (NU1608, a warning unless the application treats it as an error), rather than left unwarned on a major version the Wrapper was never tested with ([Requirements](getting-started#requirements); ADR-0205).
- **ExGrid:** `ClipboardData.Assemble` takes a header's raw form, `headerRawAt`, for the HTML flavour of a copy with headers, so Excel reads a rounded numeric header in full while plain text keeps its shown form; a header with no raw form and ExGrid's own grids copy as before. The optional fifth parameter replaces the four-parameter signature: rebuild calling assemblies, and replace a four-argument method-group conversion with a lambda or a five-argument delegate; direct calls can omit the new argument ([Copy](exgrid/clipboard#copy); ADR-0005, ADR-0201).
- **ExGrid:** Some public signatures grew an optional parameter since `0.1.0-beta.2`, so code compiled against it is compiled again, and a positional deconstruction takes one more variable: `GridSource.Fetch` takes `summarize`, `rowKey` and `clock`, and the Chrome's `ColumnMenuContext`, `ContextMenuContext`, `FilterPanelContext` and `FindContext` take `TakeFocus`. Code that calls them by name or position compiles unchanged. `EditDiscardReason`'s values each moved down one when `OrderChanged` left (#70), so a reason stored as a number is read again (ADR-0130, ADR-0141, ADR-0204).
- **ExGrid:** The stylesheets are placed as components, not linked by path: replace your `<link>` to `_content/ExGrid/ex-grid.min.css` with `<ExGridStylesheet />` in `App.razor`'s `<head>` in a Blazor Web App, or add it as a root component at `head::after` in a standalone application, and do the same with `<MudExGridStylesheet />` for ExGrid.MudBlazor. Each component, and the grid's own script import, asks for the file the package was built with, so a normal reload after an upgrade brings the new files, on GitHub Pages too; `<ImportMap />` is no longer needed for the grid's script ([Link the stylesheets](getting-started#link-the-stylesheets); ADR-0123).
- **ExGrid:** `ExGrid.Columns.AutoWidth` is no longer public, and neither is `ColumnWidthSpec.ResolveWidthPx`, which took it: it tracks the widest value an Auto column has painted (ADR-0016). Nothing replaces it; a Consumer declares `ColumnWidth.Auto` and the grid resolves it (ADR-0201).
- **ExGrid:** `ExGrid.Components.CellClasses` is no longer public: it composes the classes a cell wears. The class names themselves stay the presentation contract a stylesheet selects by (ADR-0029), and nothing replaces the type (ADR-0201).
- **ExGrid:** `ExGrid.Clipboard.FillDecision` is no longer public: it is the grid's verdict on a fill key before it asks anyone. A Consumer receives an approved fill as a `GridPasteIntent`, and hears a refusal as a `PasteRefusalReason` through `OnPasteRefused` (ADR-0201).
- **ExGrid:** `ExGrid.Clipboard.FillPlan` is no longer public: it is the grid's plan for the fill keys, Ctrl+D and Ctrl+R. A Consumer receives a fill key as a `GridPasteIntent` whose `FillSource` names the range it fills from (ADR-0201).
- **ExGrid:** `ExGrid.Clipboard.ClipboardBlock` is no longer public, and neither is `ClipboardParse.ParseBlock`, which returned it. `ClipboardParse.Parse` reads the same values, and a paste's `GridPasteIntent` carries where each field came from (`Origins`, `OriginFor`) (ADR-0201).
- **ExGrid:** `ExGrid.Clipboard.ClipboardPayload`, what the grid hands its own script to put on the clipboard, is not the contract: it is hidden from a Consumer's editor and may change in any version. Since `0.1.0-beta.2` its constructor and deconstruction take the copy's `Landing`. A Consumer answering a copy through `CopyAnswer` receives a `GridCopyRequest` and answers with a `GridCopyAnswer`, never a payload (ADR-0201).
- **ExGrid:** `ExGrid.Clipboard.ClipboardRules` is no longer public: it is the grid's own planning of a copy, a paste and a fill key. A Consumer answering a copy or a paste reads the plan the grid hands it (`GridCopyRequest.Plan`, `GridPasteIntent.Plan`), and `CopyCellCap` still defaults to the 1,000,000 cells `ClipboardRules.DefaultCellCap` named (ADR-0201).
- **ExGrid:** `ExGrid.ColumnGeometry` is no longer public, and neither are `ColumnStyles`' constructor and `Geometry`, which named it: it is the grid's own horizontal slicing (ADR-0004, ADR-0013). Nothing replaces it; a Consumer declares widths on its columns and hears a resize as a `ColumnWidthChange` (ADR-0201).
- **ExGrid:** `ExGrid.Clipboard.CopyDecision` is no longer public: it is the grid's verdict on a copy before it asks anyone. A Consumer answering a copy receives the approved plan as `GridCopyRequest.Plan`, and hears a refusal as a `CopyRefusalReason` through `OnCopyRefused` (ADR-0201).
- **ExGrid:** `ExGrid.Selection.CycleOrder` is no longer public, and neither is `GridSelection.CycleFocus`, which took it: the order Enter and Tab walk the Focus in is the grid's (ADR-0012). Nothing replaces it (ADR-0201).

## Behaviour changes

- **ExGrid:** On Blazor Server, a key typed after a menu command had opened a popover in the menu's place — ExSheet's Format Cells… from the Context Menu, or your own `OpenPopoverAsync` called from a command — but before the popover took the keyboard was lost or not as the round trip fell, because the keyboard was on nothing; now it lands on the grid, which holds it and hands it to the popover in order once that holds the keyboard. A Tab or Shift+Tab typed in that gap is now dropped with every key behind it, where a Shift+Tab could enter Format Cells at Cancel before; pressed once Format Cells holds the keyboard, it wraps as ever ([Format Cells](exsheet/formatting#format-cells); ADR-0039, ADR-0010).
- **ExGrid:** Two `GridQuery` values are equal when they ask for the same range, sort and filter, compared by what their lists and filter hold rather than by which lists hold it, so a query read back through `GridViewStateJson.ReadQuery` equals the one written. Before, two queries built from separate lists were never equal; a cache keyed by a `GridQuery` now finds a repeated ask ([A server, a page at a time](exgrid/data#a-server--a-page-at-a-time); ADR-0207).
- **ExGrid:** A render of the Consumer that hands the grid nothing new — the same Window holding the same rows where they are painted, the same Columns and the same delegates — no longer renders the grid at all, where before it rendered the grid's root once; restyling the element around the grid now costs no .NET render (ADR-0027).
- **ExGrid:** One commit at a time: while your `OnEdit` handler runs, the editor stands, and a press made meanwhile waits for your answer and is then answered against what it left, so one commit raises one Edit Intent ([Editing while values change](exgrid/editing#editing-while-values-change); ADR-0142, #70).
- **ExGrid:** A move the grid makes, and the editor opening, now bring the cell into the window at the nearest edge, so a grid taller than the window scrolls the page with the Focus; a resize never does. A page with a fixed bar sets `scroll-padding` on its scrolling element, or a cell may be brought in under the bar ([The page follows the Focus](exgrid/selection#the-page-follows-the-focus); ADR-0204).
- **ExGrid:** A refused copy, paste, fill or Delete is now announced once in the grid's live region, in English words that say what to do next, under both Chromes; a page that also announces a refusal itself from `OnPasteRefused` or `OnCopyRefused` will be heard twice. Replace the words through `CommandLabel` (or `MudGridChrome.Label`) by the ids in `RefusalLabelIds`, or answer the empty string to silence one and say it yourself ([What a refusal sounds like](exgrid/clipboard#what-a-refusal-sounds-like); ADR-0203).
- **ExGrid:** An error among the cells an answerer folds in through `GridSummaryCells.AddError` now leaves Numerical Count as well as Count, as Excel's status bar does; Average, Min, Max and Sum are still shown nowhere. A Consumer that shows Numerical Count will see it beside Count where it saw Count alone ([Status-bar figures](exgrid/selection#status-bar-figures); ADR-0130).
- **ExGrid:** The rows a screen reader is given now count the header's rows first: the header row is `aria-rowindex` 1, each tier of Header Groups is a row of its own above it, and `aria-rowcount` is the data rows' total plus those rows. So the grid writes a row's number the same way near the top, where NVDA and Narrator counted the rows before it, and far down; Chromium's accessibility tree is what checks it, and what a screen reader says of a row far down is learned from users' reports (ADR-0033). A test or script that reads `aria-rowindex` as a row's position, or `aria-rowcount` as the number of rows, now subtracts the header's rows (none while `HideHeader` is set); ExPivot's report counts its column Items' rows the same way ([The keyboard](exgrid/selection#the-keyboard); ADR-0033).
- **ExGrid:** The selection a `CycleReference` function answers is placed as given where the F4 key carried a selection, or a caret the user had moved in that text with a key or a press; where the caret stood where typing, the edit's opening or an earlier F4 left it, the grid collapses it to a caret at its end (`SelectionEnd`), in any editing state — as Excel was seen to place them after a selection, a caret moved by a key and a caret left by typing, a press and the edit's opening by generalisation. While pointing, the function is now asked with a selection over the whole Reference the outline wrote, so a pointed range's two ends cycle together, and the caret stands at the end of the answer: the rewritten Reference wears Point's own look and is not selected in the field, where a key typed would replace it. A function that answered a selection over what it rewrote now sees it selected only after a move or over a selection; one that answers a caret sees no change (ADR-0051).
- **ExGrid:** Typing over a cell's value, Shift+Home, Shift with an arrow, and the Primary Modifier (Ctrl, or ⌘ on a Mac) with an arrow, with Shift or without, now commit the edit and then extend the selection, or move or extend it to the edge, from that cell, where they selected the editor's text or moved its caret — as Excel's Enter mode was seen to do with Shift+Home, Shift+→, Shift+↓, Shift+←, Ctrl+→ and Ctrl+Shift+→, the other directions by generalisation; a value the column's verdict rejects holds the edit, as for the arrows. In Caret — after F2 in a cell (or a double-click), and in the Formula Bar until F2 takes it to Enter mode — they still move the caret or select the text, and Shift+End is unchanged ([Editable columns and the Edit Intent](exgrid/editing#editable-columns-and-the-edit-intent); ADR-0010).

- **ExGrid:** A grid that can summarise, as every grid bound to `GridSource.From` can, now shows the Selection Summary's line under its rows, and the line takes its height from the grid's. `ShowSelectionSummary="false"` takes it off; `OnSelectionSummaryChanged` is still told the figures ([Status-bar figures](exgrid/selection#status-bar-figures); ADR-0130, #65).

- **ExSheet:** Until Excel has been asked, these are `#VALUE!` where they gave a number or another Error Value: `XNPV` at a rate of exactly 0 whose values and dates are otherwise in order, where its last addition nearly cancels, so that Excel's adjustment of a last addition would give 0, and where an Error Value in its rate, values or dates fails beside another check that gives another answer (a rate below 0 or of 0, counts that differ, a date before the first wherever it lies, a cell that is not a number, or a different Error Value anywhere among them), where it gave the first Error Value it read; `PV` at a rate of -1 with a number of periods above 0, where it gave `#NUM!`; and `PMT` at a rate of -1 with a number of periods other than 0, at a rate below -1 with a whole number of periods or a fraction whose reciprocal is odd, where a quantity some evaluation of it computes passes a double's range or falls below its normal numbers (a rate, a value or a growth near those edges, such as `=PMT(1,1020,1000)`), where 1+rate raised lies below 2^-52, with no periods at the start of each period, and where an evaluation of it would magnify its own roundings more than 2^6 times, so that the evaluations give 0, numbers of the other sign or of a few digits, or an Error Value (where the present value grown and the future value nearly cancel, as in `=PMT(0.1,2,1000,-1210)`, or a number of periods is tiny at the start of each period), where it gave a number, `#NUM!` or `#DIV/0!`. - **ExSheet:** `XNPV` at a rate below 0 is `#NUM!`, where it gave a number above -1 and, at -1 or below, for some arguments: Excel gave `#NUM!` at every negative rate it was asked, -0.5, -1, -1.5 and -2, and between -0.5 and 0 the `#NUM!` is ExSheet's own until Excel has been asked. - **Fixed:** A Formula whose `INDIRECT` or `OFFSET` reads a cell of a Spill Range now follows that spill when it is blocked or freed; it used to keep the Value the cell had before. To see it, a recalculation computes every volatile Formula once more after each layout of the spills that changes something: twice in all when a change blocks or frees one spill, and only once when no spill moves ([Arrays that spill](exsheet/formulas#arrays-that-spill); ADR-0124, ADR-0125).
- **Fixed:** Under `ExSheet.MudBlazor`, keys typed as Format Cells closes from Escape, OK or Cancel are the Sheet's, in order: on a Blazor Server circuit ↓ typed straight after Escape was lost, and now moves the Focus. OK sets what was touched as it is pressed, so a key typed after it changes nothing it sets ([Format Cells](exsheet/formatting#format-cells); ADR-0071).
- **Fixed:** A key typed while the keyboard is on its way back from the Sheet Toolbar, or out of one of its lists, reaches where the keyboard lands, in order: Enter straight after a KeyTip's command, after Enter on an item, or after a choice in a list moves the Focus, and Escape straight after Alt, H, O, E closes Format Cells. On a Blazor Server circuit it pressed the last toolbar item again or chose the same colour twice, and under `ExSheet.MudBlazor` a key typed in a list as it closed was dropped ([The Sheet Toolbar](exsheet/formatting#the-sheet-toolbar); ADR-0100, ADR-0050).
- **Fixed:** KeyTips can be typed at once: the letters typed before the KeyTips have taken the keyboard are held and handed to them in order, so on a Blazor Server circuit Alt, H, 1 typed straight off sets bold instead of opening an edit holding "h1" (a Tab among them is dropped with the keys after it). An Alt typed while keys are still held — straight after Enter on an edit, a second Alt, or in a list as it closes — has the outcome it has when typed slowly: Enter, Alt, H, 1 commits the edit and sets bold below it, Alt, Alt, H, 1 turns the KeyTips on and off and types "h1", and Escape three times in a list a KeyTip opened, then Alt, H, H, opens the Fill's list. Alt released before the ↓ of Alt+↓ no longer shows the KeyTips ([The Sheet Toolbar](exsheet/formatting#the-sheet-toolbar); ADR-0100, ADR-0050).
- **Fixed:** In the built-in Chrome's Sheet Toolbar lists, arrow keys typed at once land where they lead: on a Blazor Server circuit, ↓ then → in the Fill palette could leave the keyboard on the first swatch, because the late arrival of the first move's focus put the place back. Enter and Space make the choice the keys have reached, from the list's own key handling rather than the browser's press of the focused button: Enter typed straight after ↓ chose the choice ↓ had left, and Enter held while the list opened (Alt, H, H, ↓, →, Enter at once) chose nothing ([The Sheet Toolbar](exsheet/formatting#the-sheet-toolbar); ADR-0100, ADR-0039).
- **Fixed:** Keys typed on the Sheet Toolbar while one of its lists opens from the keys are the list's, in order, under either Chrome: on a Blazor Server circuit Alt, H, H, then ↓, → and Enter typed at once fill the cell from the palette, where before the arrows and Enter were the toolbar's, opening the list again or pressing the item ([The Sheet Toolbar](exsheet/formatting#the-sheet-toolbar); ADR-0100).
- **Fixed:** Under `ExSheet.MudBlazor`, a Sheet Toolbar list opened from the keys — a KeyTip such as Alt, H, F, C, Enter on Number Format, ↓ on a split control — takes the keyboard into its choices, as the built-in Chrome's does, and answers the built-in list's keys: the arrows, Home and End move, swatches ten across; Enter or Space chooses; Escape closes it. Before, the keyboard stayed on the toolbar, Escape left the list standing, and the next list opened beside it ([The Sheet Toolbar](exsheet/formatting#the-sheet-toolbar); ADR-0100, ADR-0039).
- **Fixed:** Under the built-in Chrome, More Number Formats… in the Sheet Toolbar's Number Format list opens Format Cells in the list's place, as Format Cells… does from the Context Menu: the grid is told the keyboard is going to Format Cells before it takes it back from the closing list. On a Blazor Server circuit the list was closed first, and a key typed in the moment between the two could reach the grid instead of Format Cells. Under `ExSheet.MudBlazor` the hand-off to Format Cells' dialog was told while the toolbar's closing list still held the keyboard, and so taken as reached there: Escape typed straight after More Number Formats… went to the grid and Format Cells stayed open. It is now told once the toolbar has given the keyboard back through the grid, and the keys handed back go on to Format Cells. The dialog's first render also follows that hand-back, so its focus cannot overtake the keyboard and keys returning from the toolbar ([The Sheet Toolbar](exsheet/formatting#the-sheet-toolbar); ADR-0039, ADR-0100, ADR-0050).
- **Fixed:** On the Blazor Server host, giving the keyboard back from the Sheet Toolbar, and opening `ExSheet.MudBlazor`'s Format Cells, no longer logs Chromium's "Blocked aria-hidden on an element because its descendant retained focus" while the browser's accessibility tree is on, as it is under a screen reader: the empty element the keyboard passes through on its way out of a MudBlazor list or into Format Cells is no longer `aria-hidden`, and the toolbar's band now gives the keyboard back from itself, through no element of its own (ADR-0100, ADR-0071).
- **Fixed:** Under `MudSheetChrome` the Sheet Toolbar is one Tab stop, as under the built-in Chrome: Number Format's button and the arrows of Font Colour, Fill and Borders no longer take Tab. They are drawn by the Chrome itself now, out of the Tab order, and open a MudMenu that draws no button of its own ([The Sheet Toolbar](exsheet/formatting#the-sheet-toolbar); ADR-0100).
- **Fixed:** One or several whole columns selected from their Headings show the fill handle at the top-right, beside the Heading, and whole rows at the bottom-left, as Excel did (observed: one column and one row by the Windows run of 2026-10-11, h3, several by the readings of 2026-10-12, R5 (2)), and every cell (Ctrl+A) shows none, as Excel showed none in view (R5 (1)). Dragged across (down), one whole column (row) fills every row (column) of the target, text copied, a Formula filled, and a lone number going on by one while one cell's handle still copies it, as Excel did (observed, R5 (3) and (4)); dragged along the axis it spans, nothing changes (R5 (3) and (4)). A fill from several whole columns or rows is refused where a line holds a number beside a blank, as any such pattern is. A fill from whole columns or whole rows, by the handle or, over whole rows, by Ctrl+D, records the source's column (row) format on the target columns (rows) and writes only the cells that hold something, so its cost is those cells, not a million: column C made bold and filled into D:E records bold on D and E, where each of their two million cells was written bold before. Ctrl+R over whole columns is refused as too large, with the notice a paste of more than a million cells gives ([A first sheet](exsheet#a-first-sheet); ADR-0050).
- **Fixed:** The fill handle continues the one number of a source that holds nothing else, as Excel does: `1` over an empty cell, dragged right, gives `2 3`, where it gave `1 1`, and columns B:C with B1 `1` and C1 empty, dragged right, give D1 `2` and leave E1 empty, where the fill was refused. A single number in a line of a source whose every cell holds a number is still copied, as Excel copies it; beside text, a boolean or a gap between numbers, the fill is refused rather than copied, since Excel was not read there ([Overview](exsheet); ADR-0050).
- **Fixed:** In a Selection of several ranges, the active cell's thin border now has a white line of one Device Pixel outside it on its top and left, between it and the gridline, and the cell's own ground on its right and bottom, so a filled active cell shows its Fill there and white on the other two sides, as run 18a observed Excel's with D4 filled yellow (at Excel's 100% and 150% zoom on a 150% display); before, the Fill showed on all four sides. `--ex-sheet-selection-ring` colours the line ([Borders](exsheet/formatting#borders); ADR-0008, ADR-0071).

## ExPivot

- **Added:** The Field List has a close button beside its title, which the Pivot Toolbar's toggle reopens, and a field dragged from an Area onto the report is removed from the layout, as a drop on the list of fields removes it; Σ Values is never removable ([The PivotTable Fields pane](expivot/layout#the-pivottable-fields-pane); ADR-0061, #63).
- **Added:** The report's header shades and colours the letters of each selected column, with a two-device-pixel line along its bottom edge including the pinned label column; a whole column takes a distinct shade, including when several ranges together cover it. `--ex-heading-mark`, `--ex-heading-mark-background` and `--ex-heading-mark-whole-background` set the line, letters and shades, with the Focus outline's colour as the mark's default; Themes take precedence, ExPivot.MudBlazor uses its palette, and the header follows the frame's colour scheme. Where the header covers a Focus or single-range side, the mark supplies its two device pixels without a second outline; at the pinned block the outline stays inside the cell, with a two-device-pixel default at every display scale and forced colours preserving the Focus border and Heading Mark in Highlight ([Report forms, subtotals and grand totals](expivot/layout#report-forms--subtotals-and-grand-totals); ADR-0008, ADR-0059).
- **Added:** A report shows Excel's status-bar figures over the selected cells, in the Value Field's format; as in Excel, a subtotal or a grand total that is selected is summed with the rest ([Report forms, subtotals and grand totals](expivot/layout#report-forms--subtotals-and-grand-totals); ADR-0130, #65).
- **Added:** A report a server computes: `ReportSource` takes a `PivotReportSource`, whose server runs the same engine (`PivotReportSource.From`) and sends only the Windows the grid shows, then Window Changes checked by a Window Digest. `PivotReportSource.Fetch` carries your transports, `PivotReportJson` writes their questions and answers, and a remote report recovers a missing Baseline Window by itself ([A server's source](expivot/sources#a-server-s-source); ADR-0151, ADR-0152, #70).
- **Fixed:** A Field List menu closes when the user presses elsewhere in the same ExPivot, or moves the focus away, and Escape still reaches it after a press on a disabled command; menus and panels stay anchored to their entry while the Field List scrolls ([The PivotTable Fields pane](expivot/layout#the-pivottable-fields-pane); ADR-0061, #63).
- **Fixed:** A live report's redraw shares what an update did not change, so the browser's heap levels off where it grew with every redraw until it ran out, and a live update is faster; what a live ExPivot keeps is bounded by the reports the Change Highlight compares. The first report, and in the browser a new question over 27,000 combinations or more, take longer than before, as `verification/2026-10-10-linux-merged-live-costs` records ([The Change Highlight](expivot/live#the-change-highlight); ADR-0153, #70).
- **Fixed:** Changing `OrderKeyPolicies` on a report already shown now asks for the report again, as a new layout does, so the Items are reordered by the policy the parameter names. Before, the report kept its old order until something else asked for it. The same policies handed again, in a new dictionary, ask nothing ([An Order Key on a server](expivot/layout#an-order-key-on-a-server); ADR-0152).
- **Fixed:** Keys typed as Show Details' dialog closes, or as a field's menu or panel closes from inside, go where the keyboard lands, in order, under either Chrome: on a Blazor Server circuit ↓ typed straight after Escape in the dialog was lost and the report's Focus stayed put, and Enter typed straight after Escape in a field's menu ran the menu's first command. Now ↓ moves the report's Focus, and Enter is the field's button's, opening its menu again. A menu or panel stays on the page until the keyboard has left it, and its commands and OK do nothing meanwhile ([Show Details](expivot/values#show-details); ADR-0061, ADR-0070).
- **Fixed:** Keys typed on a field's entry, on Layout ▾ or on a report filter while its menu or panel opens are the menu's or the panel's, in order, under either Chrome: on a Blazor Server circuit Enter typed straight after the Enter that opened a field's menu pressed the entry again and closed the menu, and now presses the menu's first command, as typed slowly; letters typed straight after Enter on a report filter are typed into its Filter…'s search while the report is shown. `PivotItemFilterContext` gains `TakeKeyboard`, through which the search takes the keyboard; a Chrome of your own that focuses its search by its own `FocusAsync` still works, but a letter typed in the moment the search takes the keyboard can then overtake the held ones. The Pivot Toolbar now stands inside an element of ExPivot's own, `ex-pivot-toolbar-keys`, which hears its keys and draws no box (`display: contents`): a selector of yours that names the toolbar as a direct child of `.ex-pivot-report` names that element instead ([The PivotTable Fields pane](expivot/layout#the-pivottable-fields-pane); ADR-0061).
