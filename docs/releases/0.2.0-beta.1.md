# 0.2.0-beta.1

Published: 2026-11-03
Packages: ExGrid, ExGrid.MudBlazor, ExSheet.Engine, ExSheet, ExSheet.MudBlazor, ExSheet.Xlsx, ExGrid.Data, ExGrid.Data.Arrow, ExGrid.Data.Xlsx, ExPivot.Engine, ExPivot, ExPivot.MudBlazor, ExChart.Engine, ExChart, ExChart.MudBlazor, ExBoard
Target: net10.0

## Highlights

- The whole family now runs on one core written in TypeScript, and React takes it as Blazor does: ExGrid, ExSheet, ExPivot, ExChart and ExBoard are published to npm under `@ex-grid` (from [0.2.0-beta.2](release-notes#0-2-0-beta-2): this version's npm publish failed before it wrote any package), with Mantine and MUI Wrappers beside the built-in Chrome, and the Blazor packages wrap the same script, so both behave alike ([React](getting-started/react); ADR-0350, ADR-0370, ADR-0390).
- ExChart, Excel's charts drawn from the grid or from a Chart Spec, and ExBoard, a board of grids, pivots and charts an application or an AI composes once ([ExChart](exchart), [ExBoard](exboard)).
- Validation that answers later: a verdict or an edit may be a promise, the input typed behind it waits for it, and a rule may judge the whole collection, with F8 stepping through the errors ([Validation](exgrid/editing#validation); ADR-0380, ADR-0381).
- Expandable Header Groups: a header group draws a toggle and tells you, and you hold its columns ([Pinned columns and Header Groups](exgrid/columns#pinned-columns-and-header-groups); ADR-0400).
- `.xlsx` read and written by the Snapshot and by ExSheet's Workbook ([.xlsx](exsheet/xlsx)).

## Breaking changes

- **ExGrid:** `RowHeadings`, `NameBoxLabel` and `DataEdge` on `ExGrid.Components.ExGrid`, and the new `FindMatch`, take a `ScriptFunction`, a function exported from a JavaScript module the application serves, which the browser calls as it draws and moves (ADR-0431), in place of a .NET delegate: a page passes `ScriptFunction.Of(module, export)` and serves the module (ADR-0440).
- **ExGrid:** `PointAt`, `ReferenceText`, `CycleReference` and `ReferencesIn` on `ExGrid.Components.ExGrid` take a `ScriptFunction`, naming a function exported from a JavaScript module the application serves, in place of a .NET delegate: the browser calls it as it decides each key in the editor, on Blazor Server as on WebAssembly (ADR-0431). The modules load before the grid is drawn: a function first given later is refused by name, and a module that does not load is said in the grid's place. `ReferenceColour.Reported` is new, for an adapter reading back a colour the Script Core handed out (ADR-0431).
- **ExGrid:** A tick of the find panel's Match case or Match entire cell contents is now a click taken in its place in the Input Order, under the built-in Chrome and `MudGridChrome` alike: a step clicked straight after a tick searches with the option ticked, and one clicked before it with the option as it stood, at machine speed and over a round trip. `FindContext.MatchCaseChanged` and `WholeCellChanged` are now `Func<bool, Task>` where they were `Action<bool>`, so a Chrome of your own that draws the find panel returns the task from its option's change handler (`ValueChanged="Context.MatchCaseChanged"` binds as it did), and puts `data-ex-claims="click"` on the checkbox itself, not on a label around it (ADR-0240).
- **ExGrid:** `ExGrid.Components.ExGrid<TRow>` is drawn by the Script Core in the browser in place of .NET: the name, the `Source` or `Rows`, the `Columns` and the callbacks stay, so a page keeps `@using ExGrid.Components`, and `ExGridRow<TRow>` and the logic only the grid drawn in .NET ran are removed. A server's rows come through `GridSource.Fetch`: the grid takes no `Window`, `WindowStart` or `OnRangeNeeded`. `IGridChrome` keeps `ScriptSlots`, `Stylesheets` and the view overloads (`ColumnMenu(GridMenuView)`, `ContextMenu(GridMenuView)`, `FilterPanel(GridFilterView)`, `LoadingIndicator(GridLoadingView)` and the rest); the context overloads and their records (`FilterPanelContext`, `FindContext`, `CellEditorContext`, `ColumnMenuContext`, `NameBoxContext`, `FormulaBarTextContext`, `EditorCompletionContext`, `LoadingContext`, `CellMessageContext`, `SelectionSummaryContext`) are removed, since a Chrome now fills only the Script Core's slots, its controls marked with `ScriptSlotAttributes`. The Script Core draws the Selection Summary and a cell's message itself. `ContextMenuContext<TRow>` loses the members of the menu drawn in .NET and is `(Row, Column, Type, Selection, RowSequenceVersion, Close)`. `GridPointedAt<TRow>` holds only `InBrowser`, and `GridPointedInBrowser<TRow>` takes no `taken` callback. The C# key tables and rules the grid drawn in .NET decided by (`MenuKeys`, `MenuKeyResolver`, `ClipboardParse`, `ClipboardPayload`, `OperandReading`, `FilterPanelChoices`, `ChangeHighlightRules`, `EditorReference`, `EditorRewrite`, `PointState`, `GridPointArrow`, `GridPointDashes<TRow>`, `GridPointedPress<TRow>`, `GridPointedStep<TRow>`, `HeldSelection`, `HeldSummaryFigures`, `FindOutcome`, `GridActionRefusal<TRow>` and `GridCommitRefusal`) are removed: the Script Core decides each in the browser, and a refusal reaches `OnRefused` as before. In ExGrid.MudBlazor, the parts drawn for the grid drawn in .NET (`MudExGridMenu`, `MudExGridFilterPanel`, `MudExGridFindPanel`, `MudCellEditor`, `MudEditorCompletion`, `MudNameBox` and `MudFormulaBarText`) are removed; `MudGridChrome` draws the same surfaces over the Script Core (ADR-0370).
- **ExSheet:** `ExSheet.Engine` is rebuilt around `Workbook`, with no forwarders kept: `new Sheet(culture)` is now `new Workbook(culture)`, whose one Sheet is `Sheet1`, and `new Sheet(culture, name)` is `new Workbook(culture, [name])`; the Sheet is `workbook.Sheets[0]`, read through `GetValue`, `GetDisplay`, `GetCellFormat` and their peers (ADR-0331).
- **ExSheet:** `Sheet.Open(document)` is now `Workbook.Open(document)`, which opens a Sheet Document as a Workbook of that one Sheet, and `sheet.ToDocument()` is `workbook.ToDocument(sheet.Name)` (ADR-0331).
- **ExSheet:** `sheet.Do(edit)` and `sheet.Check(edit)` are now `workbook.Do(sheet.Name, edit)`, which returns a `WorkbookStep`, and `workbook.Check(sheet.Name, edit)`; `sheet.Enter`, `SetEntries`, `InsertRows`, `DeleteRows`, `InsertColumns`, `DeleteColumns`, `SetNumberFormat`, `SetAlignment`, `SetCellFormat`, `SetColumnWidth` and `SetAutomaticColumnWidth` are `workbook.Do(sheet.Name, …)` with the `SheetEdit` of the same name, and what the edit changed on the Sheet is `step.Change.For(sheet)` (ADR-0331).
- **ExSheet:** `sheet.DeclareLinkedTable`, `sheet.PushLinkedTable` and `sheet.LinkedTables` are now the `Workbook`'s members of the same names, as the tables are read from every Sheet (ADR-0331).
- **ExSheet:** `sheet.Today`, `SetToday`, `NowSource`, `RecalculateVolatile` and `HasVolatileFormulas` are now the `Workbook`'s members of the same names, which answer for every Sheet, so a Sheet added or copied reads the Sheet Day too, where it showed `#GETTING_DATA` before (ADR-0331).
- **ExSheet:** `sheet.Seed`, `Changes` and `SetSeed` are now the `Workbook`'s members of the same names, and `SetSeed` answers a `WorkbookChange`. A change on any Sheet now draws `RAND` and `RANDBETWEEN` again on every Sheet, as Excel does, and a draw names its Sheet, so the same seed and count give different draws than before and `=RAND()` at the same cell of two Sheets draws two numbers (ADR-0180).
- **ExSheet:** `ExSheet.Components.ExSheet`'s `ToolbarContent` is drawn by the Script Core: a `ToolbarButton`'s `OnClick` runs in .NET before the Sheet takes the next key, and its `ChildContent` is drawn from your markup (a Chrome that draws the item marks its place with the new `SheetScriptSlotAttributes.Content`, told by `SheetToolbarItemView.HasContent`). A Toolbar Item of your own derived from `ToolbarItemBase`, a KeyTip on one of ExSheet's items and a `ToolbarRow` without a `Label` are refused by name. The Script Core's `SheetHandle` and `@ex-grid/sheet-react`'s ref gain `tell(sentence)`, which says a sentence in the Sheet's notice (ADR-0100).
- **ExSheet:** `FormatCellsContext` no longer has `ReturnKeyboardFrom` or `HoldKeysForPopup`: a Chrome's own Format Cells no longer holds the keys typed on the way itself. It uses `InOrder` for a claimed control's handler, `JoinSurface` for a dialog or popup drawn outside the Sheet, `HandKeyboardToFrame` and `TakeKeyboard` to bring the keyboard to it, and `ReturnKeyboard` to give it back; the Sheet holds the keys meanwhile. Under ExSheet.MudBlazor, the Format Cells dialog and its More Colours popup are in the Sheet's order — Escape, OK, Cancel, × and More Colours' opener are handled in their place, and what is typed after them goes where they leave the keyboard — and `MudFormatCellsDialog` loses its `KeysArrive` and `KeyWhileClosing` parameters, which only the Wrapper set ([Format Cells](exsheet/formatting#format-cells); ADR-0240).
- **ExSheet:** `ExSheet.Components.ExSheet` is drawn by the Script Core in the browser in place of .NET: the name, the document, the Workbook, the toolbar and the commands stay, so a page keeps `@using ExSheet.Components`. Its reads cross to the browser, so `ToDocument`, `CellFormatAt` and `LinkedTables` are `ToDocumentAsync`, `CellFormatAtAsync` and `LinkedTablesAsync`. `ISheetChrome` keeps the Script Core's slots (`SheetScriptSlots`, `ToolbarItem(SheetToolbarItemView)`, `FormatCells(SheetFormatCellsView)`, `SheetTab`, `SheetTabAdd`); the context overloads and their types (`ToolbarItemContext`, `ToolbarItemFace`, `ToolbarChoice`, `SheetToolbarContext`, `FormatCellsContext`, `SheetFindContext` and the Sheet Tab menu's) are removed, as are `FontToggleItem`, `ColourItem`, `AlignmentItem`, `ToolbarButton.GivesKeyboardBack` and `ToolbarItemKind.Separator`. A Toolbar Item now only declares where it stands, and `ToolbarItemBase` cannot be derived: a button of your own is a `ToolbarButton`. In ExSheet.MudBlazor, the Format Cells dialog, toolbar items, find panel and tab menu drawn for the Sheet drawn in .NET are removed; `MudSheetChrome` draws the toolbar, the Sheet Tabs and Format Cells over the Script Core, and needs no `MudDialogProvider`. ExSheet still places its stylesheet notice when the stylesheet is missing or stale (ERR-11) (ADR-0370).
- **ExSheet:** `ToolbarItemContext` no longer has `ChoicesClosing` or `ChoicesOpened`, and `ChoicesClosed` now takes the choice made and whether Escape closed the list: a Chrome's own toolbar list no longer passes the keys typed on the way to the toolbar or answers the keys it hands back. It calls `ChoicesClosed` in the turn of the key or press that closes it, while it still holds the keyboard, and the toolbar makes the choice itself; it takes the keyboard through the new `TakeKeyboard`, joins the Sheet's order through `JoinSurface` when it is drawn outside the Sheet, and puts its keys and presses in their turn through `InOrder`. A list asked to open that cannot calls `ChoicesClosed` with no choice. Under ExSheet.MudBlazor the toolbar's buttons and lists are in the Sheet's order as the built-in ones are: a press on an item, and a key or a choice in its list, is answered in its place, and what is typed after it goes where it leaves the keyboard ([The Sheet Toolbar](exsheet/formatting#the-sheet-toolbar); ADR-0240).
- **ExPivot:** `PivotPopupFrame.OnFocusIn` and `OnFocusOut` are removed. The frame is ExPivot's own part, placed by ExPivot and hidden from a Consumer's editor; they carried the local queue of keys typed while a menu or a panel opened, which the pivot's Input Order replaces. Nothing replaces them (ADR-0240).
- **ExPivot:** `ExPivot.Components.ExPivot` is drawn by the Script Core in the browser in place of .NET: the name, the `PivotSource` and the `PivotLayout` stay, and its `Chrome` takes the Pivot Chrome that `PivotChrome` took. Its `ReportSource`, the report Windows a server computed (ADR-0151), goes with it: a server answers Leaf Aggregates through `PivotSource.Fetch`, and the report is built in the browser. `IPivotChrome` keeps `GridChrome`, `Stylesheets`, `ScriptSlots` and the view overloads; the context overloads (`Toolbar(PivotToolbarContext)` and the rest) and their records are removed, since a Chrome now fills only the Script Core's slots, from a view of data, its controls marked with `PivotScriptSlotAttributes`. In ExPivot.MudBlazor, the parts drawn for the pivot drawn in .NET (`MudPivotToolbar`, `MudPivotFieldList`, `MudPivotMenu` and the rest, with `MudPivotButton` and `MudPivotIconButton`) are removed; `MudPivotChrome` draws the same surfaces over the Script Core (ADR-0370).

## Behaviour changes

- **ExGrid:** A `double` in a column with no `Format` now shows at most 15 significant digits, as Excel's General does, so `0.1 + 0.2` shows `0.3` rather than `0.30000000000000004`. Sorting and filtering already compared at those 15 digits, so the cell now reads as they do. Only the shown text moves: copy's raw `text/html` carries the value whole, and the editor, the Formula Bar and Replace keep the whole number, so an edit committed unchanged writes back the same value. A negative zero shows `0`. A `decimal` is unchanged, and ExSheet, which writes its own General, is not affected. The Script Core's `number` reads the same way (ADR-0006).
- **ExGrid:** An `OperationCanceledException` thrown by `OnFind` (or a Source's find) for a step the grid did not cancel is now taken as a step the Consumer gave up: the Focus does not move, the find panel stays open with no outcome, and nothing is raised on `OnFindRefused`. Before, the exception escaped the grid. A Consumer that cannot read what it searches throws it and says why itself, rather than answering `NotFound` for cells it never read (ADR-0055).
- **ExGrid:** Blazor's ExGrid no longer reads and sends again the values of a row the browser already holds: a row whose instance is the one sent before, under the same columns and source, crosses as its id and what it paints (its Cell States, Row Kind, mark, appearance and change times), which are still asked each time. A row rewritten in place therefore does not repaint, as ADR-0003 always said and as 0.1.0 did; replace a changed row with a new instance (ADR-0350).
- **ExGrid:** A declared key the core answers itself is still refused, and its message now names the core's action in words, `the core's select all`, where it gave the member's name, `the core's SelectAll`. A Consumer that matched the old text in the exception's message matches the new one instead (ADR-0050).
- **ExGrid:** Blazor's Script `ExGrid` marks the element its script mounts on `aria-busy="true"` and `data-ex-mounting="grid"` from its first render until the script has attached, which lifts both; a refused script's root carries neither. Assistive technology hears the grid as loading instead of as an empty box, and a page or test that holds several can tell which are still to come: they attach in no set order (A11Y-20) ([Selection and keyboard](exgrid/selection); ADR-0033).
- **ExGrid:** On Blazor, a Sort or Filter the user applies is the grid's at once: the header shows it and the grid is loading until the server's rows arrive, as under a `FetchingSource`. A filter panel opened straight after OK now shows the filter just applied, where on Blazor Server it could show the one before and offer no "Add current selection". A click on the rows before they arrive is taken against the order before, and the new order drops it (ADR-0440).
- **ExGrid:** Blazor's ExGrid loads the TypeScript core from the Shared Script the ExGrid package ships beside its bridge, `_content/ExGrid/ex-grid-script.min.js`, which every product over the core on the page shares, so a page with another product beside the grid loads the core once. A Content Security Policy that lists the package's files names `ex-grid-script.min.js` and `ex-grid-core.min.js` in place of `ex-grid.min.js`, and a Shared Script of another build is refused with the reload notice, as another version's script is (ADR-0411).
- **ExGrid:** A Chrome's Razor parts stand inside the grid the browser draws: `ExGrid.Components.ExGrid` renders each beside the grid and the grid's script moves it into place and wires its controls there (ADR-0410). `MudGridChrome` draws the column menu, the filter panel, the find panel, the Context Menu and the loading bar this way; its filter panel's operators are native selects and a condition's value is typed as text for every type, so no choice reaches the grid after the Enter that applies it. A Chrome of your own names its parts in the new `IGridChrome.ScriptSlots` and answers each through the overload that takes a view (`ColumnMenu(GridMenuView)`, `ContextMenu(GridMenuView)`, `FilterPanel(GridFilterView)`, `FindPanel(GridFindView)`, `LoadingIndicator(GridLoadingView)`), marking its controls with `ScriptSlotAttributes`. Space, Delete and Backspace on a checkbox or radio button in such a part do what the browser's own control does, whatever the component library's handler would, so a box never shows a tick the grid has not heard. The element a part is drawn in draws no box of its own (`display: contents`), so a part lays itself out in its place as a React Chrome's does; a part that fills the height it is given, such as a Details dialog's records, fills it (ADR-0410).
- **ExGrid:** `OpenPopoverAsync(content, label)` on `ExGrid.Components.ExGrid` draws the Consumer's Razor in the grid's popover frame, which the browser holds, and `ClosePopoverAsync()` closes it. The contents' `GridPopoverContext` keeps `Close` and `InnerPopupChanged` and gains `InOrder(kind, work)`: a control that names its event in `data-ex-claims` and hands its work to `InOrder` keeps its place among the grid's keys and presses, so a key typed straight after OK reaches what OK left. `InOrderAsync(kind, work)` on the grid does the same for a control in a Template cell. `FocusRequest` and `FocusLastRequest` stay zero, since the grid hands the contents the keyboard itself, and the overload taking `closedByEscape` is not carried (ADR-0441).
- **ExGrid:** Measured against 0.1.0 on one machine (`spikes/render-bench/results/20261030-script-core/`): Blazor's components over the Script Core take keys up to fifteen times faster on WebAssembly and twice as fast on Server. Where .NET hands the browser data they are close to 0.1.0 or slower: a push of one row into 10,000 takes 6 ms on Server and 12 ms on WebAssembly where 0.1.0 took 3 and 4; a Window of all new rows, or any push over 100,000 rows on WebAssembly, takes 11 to 75 ms where 0.1.0 took 7 to 31; an ExSheet edit takes 19 to 129 ms on either host where 0.1.0 took 13 to 103 on Server and 99 to 641 on WebAssembly; and an ExPivot Change Batch takes about 60 ms on either host where 0.1.0 took 4 on Server and 15 on WebAssembly, spent laying the report out again in the browser (ADR-0350).
- **ExGrid:** A click on one of the grid's own controls — a heading, a column's ▾, a column menu or Context Menu item, a completion candidate, the pager, the status line's buttons, a grip's double click, a filter panel's OK and Cancel, Find's Previous and Next, the context menu on the rows and on the status line, under the built-in Chrome and the MudBlazor Wrapper alike — now takes its place in the grid's Input Order: it is handled after every key, press or click made before it and before every one made after it, on Blazor Server and WebAssembly alike, and one made while earlier keys are still being answered is held and carried out in its turn (ADR-0240). The Settled Mark waits for it. Nothing changes for a script that waited for each effect; one that sent such clicks at machine speed now gets the outcome it gets sending them slowly ([Selection and keyboard](exgrid/selection); ADR-0240).
- **ExGrid:** `ExGrid.Components.ExGrid<TRow>` is drawn by the TypeScript Script Core (ADR-0350 section 7): the keys, the Selection, the clipboard, the editor, Find and the Selection Summary run in the browser on both hosting models, while the rows, their order and what an edit does to them stay in .NET behind the same `GridColumn`s and `IGridSource`. What a row paints is answered in .NET and crosses with the row, and a Template cell's fragment is rendered in .NET and moved into its cell, so on Blazor Server a cell scrolled into view shows its content a round trip later; a verdict, a copy, a summary, Replace All, a declared key, a Find step and the Context Menu's commands are asked of .NET in their turn, the input behind each waiting for its answer. A call the browser hands .NET that is larger than a hub's 32 KB message crosses as a gzip stream, in its turn. The `ReturnKeyboardAsync` overload that collects keys typed on a joined surface is not carried. Building ExGrid from source now needs Node 26.12.1, or a release of 22 or 24 with the same fixes (22.23.4, 24.22.1), which bundles the core (ADR-0350).
- **ExGrid:** `ExGrid.Components.ExGrid<TRow>`'s fill is pending in the browser until `OnFill`'s handler completes, as a paste is (ADR-0380): a target over a column that is not Editable is refused first through `OnRefused`, a handler that calls `GridFillIntent.Refuse` leaves the Selection on the source, Escape cancels a fill whose handler has not completed, through the new `GridFillIntent.CancellationToken`, and otherwise the Selection becomes the source and the target together (ADR-0050).
- **ExGrid:** Find now searches the visible column headers and Header Group labels as well as the rows, the header rows coming before the first data row: a step that wraps past the last row, or finds no row, stops on the first header that matches (the last, backward), and the next step goes on from it. A header found is the current match: it wears `ex-match-mark-current`, is scrolled into view across, and the panel names it, "Found in the header Trader" (`FindOutcome.FoundInHeader`, `FindPanelLabelIds.FoundInHeader`, the header's text in the new `FindContext.FoundHeader`), while the header carries `aria-current="true"`; the Focus does not move. Every header on screen that matches wears `ex-match-mark`, judged by `GridFind.Matches` over its text whoever answers Find. A search for text that is also a column's header therefore stops on that header once per round. The Consumer's `GridFindRequest` and answer are unchanged. A selection of more than one cell searches no header, hidden columns' headers are not searched, Replace never writes a header, and the new `FindsHeaders` parameter (default `true`) turns it off, as ExSheet does for its column letters (ADR-0333).
- **ExGrid:** Keys held while the grid answers an earlier key or click no longer give up after two seconds: they wait for the editor, a popover or your frame to take the keyboard, however long the round trip, and a reveal's scroll, an edit's close and a field's text no longer stop waiting on a clock either. When the grid has answered everything before them and owes the keyboard to nothing, keys whose keyboard never arrived are refused, every one, and the live region says so in the words of the new `KeyRefusalLabelIds.KeyboardDidNotArrive`, which a Consumer replaces or silences through `CommandLabel` (ADR-0240). Before, they were replayed against whatever held the keyboard, or dropped silently. The keys a popover answers itself — Enter, Space, a letter or Tab on a menu item, a letter on a filter's value list, a filter or Find submitted with Enter, Tab wrapping round a popover — are now numbered too, under the built-in Chrome and the MudBlazor Wrapper alike, so nothing is left waiting on a clock. Breaking for a substituted Chrome: a menu must resolve its keys through the context's `ResolveKey` and run, close and focus through the context's delegates in the same handler, and a control or form that should keep its place says so with `data-ex-claims` and then reaches the grid every time that event comes — a filter form hands each submission to `Apply`, one that cannot be applied as the answer `Apply` refuses; a Chrome that marks nothing still works, unnumbered. The MudBlazor Wrapper's filter panel now hands a submission it cannot apply to `Apply` that way rather than dropping it ([Selection and keyboard](exgrid/selection); ADR-0240).
- **ExGrid:** Row Action and row Mark clicks now wait for earlier input, including asynchronous Consumer callbacks, and recovery of a discarded Blazor click uses the same input number. While waiting, a command follows its row only while continuously present in the Window; leaving it causes a visible refusal even if the row returns, and Consumers handling `OnMarkRefused` should handle the new `RowLeftTheWindow` reason (Source replacement still reports `SourceChanged`) ([Mark, Template and Action columns](exgrid/columns#mark--template-and-action-columns); ADR-0240, ADR-0160, ADR-0142, ADR-0043).
- **ExSheet:** A Formula with functions nested more than 64 levels deep, Excel's limit, or nested more than 256 levels deep (parentheses, signs, functions, operations within operations) is now refused as it is typed, with the reason; so is such text typed after a sign without `=`, which stays a refused Formula rather than becoming text. A Consumer will see a Sheet Document or an `.xlsx` workbook holding such a Formula refused on open, whole, where it opened before (ADR-0047).
- **ExSheet:** Blazor's Script `ExSheet` marks the element its script mounts on `aria-busy="true"` and `data-ex-mounting="sheet"` from its first render until the script has attached, which lifts both; a refused script's root carries neither. Assistive technology hears the Sheet as loading instead of as an empty box, and a page or test holding several Sheets can tell which are still to come: they attach in no set order (A11Y-20) ([ExSheet](exsheet); ADR-0033).
- **ExSheet:** A Sheet now draws its find panel through its own Chrome, so a Consumer Chrome's `IGridChrome.FindPanel` is no longer asked on a Sheet: ExSheet wraps the Chrome it is handed and draws the Sheet's panel, with Replace and Within, in its place. A Chrome of your own that drew the grid's find panel on a Sheet implements `ISheetChrome.SheetFindPanel` instead, handed a `SheetFindContext`; one that does not gets ExSheet's built-in Sheet panel (ADR-0332).
- **ExSheet:** A structured reference is stored in its Linked Table's declared case, the table's name and the column's, as Excel writes one back: `=sum(limit[line])` over `LIMIT` with a column `Line` is stored, shown and saved as `=SUM(LIMIT[Line])`. A Formula typed before its table is declared keeps the case it was typed in (ADR-0049).
- **ExSheet:** Blazor's ExSheet loads the grid core and the data from the Shared Script the ExGrid package ships, `_content/ExGrid/ex-grid-script.min.js`, so a page with a grid and a sheet loads them once. A Content Security Policy that lists the packages' files names `ex-grid-script.min.js` too, and a Shared Script of another build is refused with the reload notice, as another version's script is (ADR-0411).
- **ExSheet:** In a Workbook of several Sheets, a command names the Sheet it acts on: `DoAsync(sheet, edit)` does an edit, a Sheet operation among them, on that Sheet whether it is shown or not, and `CellFormatAt(sheet, address)` reads a cell there. `DoAsync(edit)` and `CellFormatAt(address)`, which name none, are refused with `SheetRefusalReason.SheetNotNamed` once the Workbook holds several Sheets, and work as before while it holds one; a page that adds Sheets from code names the Sheet. The new `SheetsChanged` event hears every Sheet added, deleted, renamed, moved or copied, an undo or redo of one included, with the names before and after (ADR-0331).
- **ExSheet:** EXP, LN, LOG10 and LOG to base 10, a whole POWER, ASIN, ACOS, ATAN, ATAN2 and the hyperbolic functions are now the exact value rounded once to the nearest double, computed by the engine rather than the platform's math library, so the C# engine and `@ex-grid/sheet-engine` give one double on every platform. LOG to another base, ACOT, ACOTH, COTH, CSCH and SECH are computed from those, and give one double everywhere too. PMT's refusal of a growth past 2^1100 is now drawn by the correctly rounded logarithm, so a payment at that line is answered or refused alike everywhere. A result can differ from before in its last bit: glibc rounds `=ATAN(3.8946)` to 1.31946007910341, and it is 1.3194600791034101 (ADR-0047, ADR-0370).
- **ExSheet:** `ExSheet.Components.ExSheet`'s commands that edit and format and its Linked Tables (`DoAsync`, `SetCellFormatAsync`, `SetNumberFormatAsync`, `SetAlignmentAsync`, `DeclareLinkedTableAsync`, `PushLinkedTableAsync`) cross to the Sheet in the browser, and what it refuses or throws is thrown as the C# engine throws it. A `SheetEdit` crosses as the new `SheetWire` writes it, the text both engines' shared cases send every edit through; `SheetWire` also reads a Cell Format back. On Blazor Server, a document, a save's Workbook or any other message to .NET larger than 16 KB crosses as a stream, in its turn; one larger than 256 MB is refused. A script that does not load, the circuit failing as it loads included, is refused as another version's is, so a command waiting on the Sheet is told so instead of waiting on (ADR-0370).
- **ExSheet:** `ExSheet.Components.ExSheet`'s `SetCellFormatFromFocusAsync` makes your change in .NET from the Focus cell's Cell Format as the browser read it, and sets it on the Selection. If the Selection moves, or the Focus cell's format changes, before the change reaches the browser, the change is refused with the new `SheetRefusalReason.SelectionMoved` or `SheetRefusalReason.FocusFormatChanged`, and the Sheet's notice says so. Nothing is ever set on cells the change was not made for. The Script Core's `SheetHandle` and `@ex-grid/sheet-react`'s ref gain `setCellFormatFromFocus`, which makes the change within the Sheet's turn, and `readFocusFormat` with `setCellFormatFrom` for a change made outside it (ADR-0100).

- **Added:** `createBoard` in `@ex-grid/board` draws a Board in the browser with the family's own grids, pivots and charts, raising its outputs on a confirm and its Board Diff on each change the user makes, and `@ex-grid/board-react` mounts it as the React component `ExBoard` (ADR-0370).
- **Added:** `@ex-grid/board` reads, writes and fits a Board Diff as ExBoard does, byte for byte, on cases both run, and a Board bound in TypeScript lays one over its views, names what no longer fits, and raises what the user has changed as its own (ADR-0370).
- **Added:** `@ex-grid/board` reads a Board in TypeScript, refusing what ExBoard's C# reader refuses, at the same path and in the same words, and binds it to Snapshots: a grid built from its input's shape, links that narrow the views they reach, and outputs raised only by a confirm (ADR-0370).
- **Added:** `ExBoard.Components.ExBoard` takes `Chrome`, `PivotChrome` and `ChartChrome`: the grid Chrome dresses the grids and the pivots' report grids, the pivot Chrome the pivots, its grid Chrome the report grids where no `Chrome` is given, and the chart Chrome the charts. Each part a Chrome names in its `ScriptSlots` is drawn by its Razor inside the view the browser draws, so `MudGridChrome`, `MudPivotChrome` and `MudChartChrome` dress it. `@ex-grid/board` adds `createBoardWith` and `familyMounts`, for a Framework Adapter that keeps each view's handle (ADR-0410, ADR-0370).
- **Added:** `@ex-grid/board` answers the `draw_board` tool as `BoardSpec` does, in the same words: `boardSpecTool` is the tool definition, `boardDeclarationOf(shape)` says a table's shape as a Board declares an input, `answerBoardSpec(call, tables)` reads a call, binds it and says the Board or its refusal by path, and `sayBoard` says a bound Board. `boardOfChart(spec, shapes)` makes a `draw_chart` spec a Board of one view, `boardChartViewId`. The Docs Site's ExBoard Examples all run under React (ADR-0340, ADR-0320).
- **Added:** `@ex-grid/board` binds a Board over sources held on a server, as `BoundBoard.BindAsync` does. Pass them with `createBoard`'s `sources` option or the `ExBoard` React component's `sources` prop, or bind with `bindBoardThrough`. A grid's rows are fetched a page at a time. A pivot reads the `PivotSource` the source's `pivot(narrowing)` makes. A chart is read through the source's `thin` at `boardChartPixels`, and a link from a pivot asks its `under`. Every question carries the link conditions narrowing the view. `valuesUnder` is the reference a server answers `under` as. A fetched grid whose source fails says so under the grid (ADR-0343, ADR-0344, ADR-0345).
- **Fixed:** `BoardDiff.Read` now refuses, naming the path, a pivot layout of a version it does not read, a column both shown and hidden, and an end of a chart's range past a double's range. The first two threw an exception that named nothing, and the last was read and could not be written back. `FitTo` now drops by name a grid part that would show no column, where it laid an empty grid over the view (ADR-0340).
- **Fixed:** A Board Input's JSON rows no longer round a `decimal` with more digits than a decimal holds: `0.12345678901234567890123456789` or `"79228162514264337593543950335.5"` is refused by input, row and column, as a value that does not convert, rather than handed on as money nobody wrote. A refusal of a row that is not an object now numbers the row in the invariant culture, as every other refusal of the rows does (ADR-0341).
- **Fixed:** On Blazor Server, an `ExBoard` disposed while its circuit was closing, as on leaving its page, could write `TaskCanceledException` to the host's log as an unhandled exception in the circuit. It now lets the browser's Board go quietly, as `ExGrid`, `ExSheet`, `ExPivot` and `ExChart` do (ADR-0370).
- **Fixed:** A Board whose pivot view writes a layout of a version the reader does not read is now refused, naming the layout's path, rather than failing with a `NotSupportedException` that named nothing (ADR-0340).

## Data

- **Added:** `BoardInput` names a piece of data and declares each column's kind; `Check` and `Bind` hold a source's `DataShape` against it and refuse a missing column, or one of another kind, naming the input and the column. `FromJson` makes a Snapshot from JSON rows by the declared kinds, and refuses a value that does not convert by its row and column rather than drop it or read it as zero. Refusals are a `BoardRefusedException` carrying the path (ADR-0341).
- **Added:** `@ex-grid/data`, a new npm package with no dependencies, holds a Snapshot in TypeScript and reads and writes it as Arrow exactly as `ExGrid.Data.Arrow` does: `readArrowSnapshot` (an IPC stream or an Arrow file, in slices with progress and an `AbortSignal`), `readArrowShape`, `writeArrowSnapshot` and `createSnapshot`. Both packages run the same cases under `tests/cases/arrow/`, each reads what the other writes, and a refusal says the same row, column and words; a stream whose buffers are compressed is refused, since the package carries no codec. It is published with 0.2.0 (ADR-0065).
- **Added:** A source held on a server says its shape, its columns' names and kinds, before any row. `FetchingGridSource.Shape`, `FetchingPivotReportSource.Shape` and `SnapshotArrow.ReadShapeAsync`, which reads an Arrow stream's schema alone, answer it through `IShapedSource.ShapeAsync`; a pivot source over a Snapshot answers the Snapshot's own. `BoardInput.CheckAsync` checks an input against it and refuses a source that says none (ADR-0341).
- **Added:** `@ex-grid/data` applies Change Batches: `createChangeBatch` takes the records added, the records changed and the Record Keys removed, and `applyChangeBatch` makes the next Snapshot from them whole or not at all, saying which rows left and which came, as `Snapshot.Apply` does. A refusal names the row, column and key in the same words as `SnapshotException`; both packages run the same cases under `tests/cases/data/`. It is published with 0.2.0 (ADR-0064, ADR-0067).
- **Added:** `@ex-grid/data` reads a CSV under a declared Schema: `readCsvSnapshot` takes the Schema as an object (its columns, separator, header row, encoding, blank texts and Record Key) and a `Uint8Array`, `ArrayBuffer` or `Blob`, and reads it as `CsvSchema.ReadAsync` does, in paced slices that report progress and can be cancelled. A refusal is a `SnapshotError` naming the row, column and line in the same words as `SnapshotException`; both packages run the same cases under `tests/cases/data/`. A culture is a language tag read through `Intl`; a date in a calendar other than the Gregorian or the Thai Buddhist, a standard date format in a culture, the standard format `U`, and the era (`g`) are refused when the Schema is read. Shift-JIS is decoded as the browser's decoder reads it. It is published with 0.2.0 (ADR-0064, ADR-0370).
- **Added:** `@ex-grid/data` suggests a Schema for a CSV nobody has described: `suggestCsvSchema` reads a `Uint8Array`, an `ArrayBuffer` or a `Blob` only as far as the rows sampled, and proposes each column's kind and reading with the marks `CsvSchema.SuggestAsync` makes, in the same words; both packages run the same cases under `tests/cases/data/`. The `culture` is a language tag. .NET's list separator, which breaks a tie between two separators that split every record alike, is not in the browser's `Intl`, so the package carries .NET 10's by language; a tag .NET holds no culture for is taken by its language, where .NET gives a comma. It is published with 0.2.0 (ADR-0064, ADR-0370).
- **Added:** A new package, `ExGrid.Data.Xlsx`, reads and writes the xlsx file format with nothing but the platform's zip and XML: `XlsxReader` streams a workbook's sheets, shared strings, Formulas (shared and array ones included), column widths, styles and theme colours in batches, with every worksheet element it does not read reported as an `XlsxElement` for the caller to judge, yielding and reporting progress, and `XlsxWriter` writes the same model back as a valid package. A file it cannot read faithfully is refused by name as an `XlsxException` naming its reason, part, sheet and cell: not a zip, macro-enabled, binary, legacy, encrypted, a DTD, a part that is not well-formed or cannot be inflated, a cell written twice, out of order or naming a style the file does not hold, or beyond `XlsxReadOptions.MaxUncompressedBytes` (1 GiB) or `MaxCells` (ten million) by default (ADR-0330).
- **Added:** `XlsxWriteOptions.MaxUncompressedBytes` bounds what an `XlsxWriter` writes: the package's parts together may hold at most this many uncompressed bytes, by default `XlsxReadOptions.DefaultMaxUncompressedBytes` (1 GiB), the most a file is read with, so what is written opens again. A write that would go past it is refused as an `XlsxException` with `XlsxRefusal.TooLarge`, naming the part and the sheet it met, rather than failing later with an unnamed `IOException` (ADR-0330).
- **Added:** `ExGrid.Data.Xlsx` writes an Excel Table: `XlsxSheetWriter.AddTable(XlsxTable)` adds one over a sheet's cells before its header's row, with its table part, the sheet's relationship and `tableParts`, its content type, an AutoFilter and Excel's default table style. The writer refuses a name Excel does not give a Table, one another table or defined name of the workbook has, overlapping tables, and a header whose cells do not hold the columns' names as text (ADR-0330).
- **Added:** `ExGrid.Data.Xlsx` is published with the rest of the family, at its one version: it reads and writes the `.xlsx` format on a server with no component (ADR-0042).
- **Added:** `@ex-grid/data-xlsx` reads and writes `.xlsx` in TypeScript as `ExGrid.Data.Xlsx` does, with no dependency: `openXlsx` takes a `Uint8Array`, `ArrayBuffer` or `Blob` (a `File` is read where it is asked, never whole) and reads its sheets, shared strings, styles, theme and cells a batch at a time, paced in slices that report progress and can be cancelled; `createXlsxWriter` writes sheets, rows, columns, styles, defined names and Excel Tables to a `Blob`. The zip is inflated and deflated by the browser's `DecompressionStream` and `CompressionStream` (`deflate-raw`). A refused file is an `XlsxError` with the same reason, part, Sheet, cell and words as `XlsxException`, and the writer's parts are the same text, line ends aside (.NET writes its platform's, TypeScript a line feed); both packages run the cases under `tests/cases/xlsx/`. Where the writer refuses a workbook past `maxUncompressedBytes` is where it hands each 64 KiB of a sheet to the zip, not where .NET's `XmlWriter` flushes. It is published with 0.2.0 (ADR-0330, ADR-0370).
- **Fixed:** A CSV Date column whose format names the day of the week but no year (`ddd dd MMM`) is now refused when the Schema is read, as a format with a month or a day but no year already was: .NET reads such a value in the current year, so the same file read next year would read otherwise (ADR-0064).
- **Fixed:** `ExGrid.Data.Arrow` refuses an Arrow dictionary that says it holds nulls and carries no validity bitmap to say which entries, naming the column, as it already refused such a column. Its null entries were read as text before (ADR-0065).
- **Fixed:** When two separators split every record of a file alike and their fields read equally well, `CsvSchema.SuggestAsync`'s Separator mark said the one suggested was chosen because its fields read best as numbers and dates. It now says what chose it: the culture's list separator, or, when that is neither, nothing but the order they are tried in (ADR-0064).
- **Fixed:** A CSV Date column declared with the round-trip format `o` (or `O`) now holds a value with an offset as the clock it shows, as every other format with an offset does: `2026-09-30T14:05:09.1234567+09:00` reads as 14:05:09, where it was read as 05:05:09, the instant in UTC (ADR-0064).
