Blazor's ExPivot over the Script Core (`ExPivot.Components.ExPivot`) takes a `Chrome`, and the parts a Chrome draws in Razor stand inside the pivot the browser draws, as they do on `ExGrid.Components.ExGrid`. `MudPivotChrome` draws the Pivot Toolbar, the report filter band, the Layout menu and a placed field's menu, Filter…, Field Settings…, Value Field Settings…, the Stale Report's notice, the PivotTable Fields pane, the sheet tabs Show Details opens and its dialog this way, and forwards its Grid Chrome's parts to the report grid. A Chrome of your own names its parts in the new `IPivotChrome.ScriptSlots` and answers each through the overload that takes a view (`Menu(PivotMenuView)`, `Toolbar(PivotToolbarView)`, `StaleReport(PivotStaleReportView)`, `ReportFilters(PivotReportFiltersView)`, `ItemFilter(PivotItemFilterView)`, `FieldSettings(PivotFieldSettingsView)`, `ValueFieldSettings(PivotValueFieldSettingsView)`, `FieldList(PivotFieldListView)`, `DetailsTabs(PivotDetailsTabsView)`, `DetailsDialog(PivotDetailsDialogView)`), marking its controls with `PivotScriptSlotAttributes`; the members have defaults, so an existing Chrome compiles unchanged. Over the Script Core a panel's choices are native selects in MudBlazor's outline, and OK that cannot apply yet is shown unavailable rather than disabled, so a press made before the panel is drawn again still reaches the pivot, which refuses it and says why. Space, Delete and Backspace on a checkbox or radio button in such a part do what the browser's own control does, whatever the component library's handler would, so a box never shows a tick the pivot has not heard. In the Fields pane, a press, a tick or a drop made against Areas that changed after they were drawn is refused rather than applied to the entry now in its place.
