  (WSL2). **13 projects, 11,380 passed, 0 failed, 11 skipped.** The skips are the ten
  `[Fact(Explicit = true)]` measurements (DA-17, PV-21, SH-19, ADR-0065) and the million-row
  `ConsistencyTests` run behind its switch (ST-1, Step 5). No row is FAILING on layers 1 and 2.
  (The run used `--logger trx`, which Microsoft.Testing.Platform ignores, as Step 1 says; its
  console log was kept outside the repository. It is not a Step 1 record.)
- **Layer 3 was not run for the audit.** CI's full run is the judge of layer 3; a layer-3 row is
  PROVEN here when a spec exists that would fail if the criterion broke.
- **One reader per section**, eight in parallel, each reading the tests behind each row closely
  enough to judge whether they can fail.
- **Mutation spot-checks:** 14 mutations, two per section except §21–§22. **9 were caught and
  5 survived** (FN-19, HG-10, SH-57, SH-59 survived outright; MEM-1 was caught by 0.7 % over a 5 %
  bound). Each surviving row is UNPROVEN below. Note for anyone repeating this: `dotnet test --filter`
  is silently ignored under Microsoft.Testing.Platform, so the whole project runs; use
  `-- --filter-class <FQN>`.
- **OWNED** names the branch whose work closes the gap: on origin where it exists there
  (`area-corrections`, `run17cf-aria-rows`, `run17cf-pivot-general`, `run17gh-widening`,
  `run17gh-readings`, `run17gh-glyphs`), by name otherwise.

#### Mutations

The mutations ran in the throwaway worktree `.claude/worktrees/mut-a1` at origin/main, which has since been removed. The runner seems to ignore the `--filter` I passed, because every run executed all 2069 tests of ExGrid.Components. That makes the result stronger: no test in the project caught either mutation.

1. **FN-19, the off-screen flag.** In `src/ExGrid/Components/ExGrid.razor` `SelectionIntersectsView()`, I replaced `if (range.LeftColumn < _columnStyles.Geometry.PinnedCount) return true;` with `if (range.LeftColumn >= 0) return true;`. Any range that overlaps the visible rows then counts as visible, whatever its columns. I ran tests/ExGrid.Components (2068 passed, 1 skipped) and tests/ExGrid.Tests (1702 passed). **Survived.** A selection that is scrolled out sideways is reported as on screen and loses its "(outside the visible range)" status. That is quietly wrong, which is exactly what the row forbids.
2. **HG-10, a group rectangle with virtualised leaves.** In `ComposeGroupStyle`, I computed `leftPx` from `Math.Max(group.FirstColumn, _scrollable.Start)` for an unpinned group, so `left` comes from the first painted member. I ran tests/ExGrid.Components, including HeaderGroupRenderingTests: 2068 passed. **Survived.** The test's 500px scroll never paints any member of the group, so it cannot tell "leaves in the DOM" apart from "leaves not in the DOM".

#### Gaps (UNPROVEN or BY-HAND, no owner, most serious first)

1. **FN-19, off-screen flag on the column axis.** The mutation survived. To close it, add an L2 test that selects cells in scrollable columns, scrolls sideways until they leave the screen, and asserts "outside the visible range". Add the reverse case too: a range over a pinned column counts as visible.
2. **UX-1, colours and pixels in the stylesheet.** No test exists, and the only record is from 2026-09-01. `ex-grid.css` holds bare pixel widths: `.ex-resize-grip` is 5px, and `.ex-resize-guide` and `.ex-drop-indicator` are 2px. #### Mutations

Both mutations ran in a throwaway worktree `.claude/worktrees/mut-a4` at origin/main, which is now removed.

1. **RR-2.** In `ExGrid.razor` `ResolveColumnGeometry()`, the early-return guard also required `_mutRowHeight == RowHeight`, and the rebuild set that field, so a row-height-only change rebuilt `ColumnStyles` and handed every row a new `Styles` instance. **Result: caught.** `GridMetricsWiringTests.A_row_height_change_skips_surviving_rows` failed (expected 1, actual 2). It was the *only* one of 2,069 L2 tests to fail (`--filter` is ignored under MTP, so the whole project ran). RR-2 rests on this single test.
2. **MEM-1.** `ApplyScrollOffset` allocated `new byte[TotalCount / 64]` per scroll step (about 15.6 KB per frame at 10⁶). **Result: caught, barely.** `AllocationTests.Scrolling_allocates_the_same_at_a_thousand_and_a_million_rows` failed with 29,046,952 vs 30,703,152 bytes (+5.7% against the 5% bound). A leak of half that size (TotalCount/128 per frame, about 8 KB/frame at 10⁶) would pass. The baseline is about 290 KB per scroll step, so the 5% bound only catches what scales with TotalCount at about 14.5 KB/frame or more at 10⁶ rows.
