# render-bench — 使い捨ての描画コスト計測

仕様を固める前に、**API の形が描画コストにいくら効くか**を実測するためのスパイク。
結論が出たら捨ててよい。

## 何を測っているか

行数ではなく **1 回の描画で触るセル数**がコストを決める、という仮説の検証。
データはメモリ上に用意済みで、**描画だけ**を測る（取得・ソート・フィルタは含まない
— [ADR-0001](../../docs/adr/0001-grid-takes-an-async-data-source-not-a-collection.md)
でそれらは Data Source 側に出したので、グリッドは全行を舐めない）。

4 モードを積み上げて、**設計判断 1 つあたりのコスト**を分離する:

| モード | 何を足したか |
|---|---|
| `Direct` | 抽象化なしの床。素のマークアップ、フィールド直読み |
| `Accessor` | + 列アクセサ `Func<Row, object>`（decimal が boxing される） |
| `AccessorMeta` | + セルごとのメタデータ問い合わせ（`poke` の as-of 相当。(book, metric) の辞書引き） |
| `Component` | + セルを Blazor コンポーネント化（もっさりの本命容疑） |

判定基準は **16.6ms**（60fps の 1 フレーム予算）。中央値がこれを超えると体感で
「もっさり」になる。

## 動かし方

```sh
nix develop -c dotnet run -c Release --project Bench.Host --urls http://0.0.0.0:5199
```

ブラウザで <http://localhost:5199>（WSL2 から Windows のブラウザで開く場合、
localhost が通らなければ `hostname -I` のアドレスを使う）。

1. プリセットを選ぶ（`フリック (40×20, 50行)` が最も厳しい現実的ケース）
2. **4 モードを連続計測**
3. **結果をサーバに保存** → `spikes/render-bench/results/{timestamp}.json` に落ちる

手動スクロールの体感は「フレーム計測 開始 → グリッドをスクロール → 停止して集計」。

## 測定条件の但し書き

- **Release ビルドで測ること。** Debug は別物の遅さになる。
- プログラム計測が含むのは **Blazor の描画 + DOM 反映**まで。`StateHasChanged()` は
  描画を同期的に完走させうるため、ブラウザのレイアウト/ペイントは計測区間の外に置き、
  各試行の後に 1ms 譲っている。**端から端までのフレーム時間は手動スクロールの
  フレーム計測**の方で見ること。
- ヘッドレス Chromium（`nix develop .#browser`）でも動くが、ソフトウェアレンダリングに
  なるため**絶対値は実機と乖離する**。ヘッドレスは例外の再現用、数字は実ブラウザで。
- **AOT は使っていない**（`wasm-tools` ワークロードが要る）。Release IL 実行での数字。
  AOT にすればさらに速くなる余地がある、と読むこと。
- 手動スクロールは `scrollTop` 読み取りに JS interop を 1 回挟むため、その分は
  実装依存のオーバーヘッドとして乗っている。プログラム計測の方には interop は無い。
- 5,000 行を用意して剰余で巡回している。行数を増やしても描画コストは変わらない
  ことの確認は、`TotalRows` を変えて再実行すれば取れる。
