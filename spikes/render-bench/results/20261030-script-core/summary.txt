The core comparison (ADR-0350 section 15), 2026-10-30: the Script Core beside the C# core it replaced, run
one after the other on one machine (a 4-core cloud container, headless Chromium 153, device pixel ratio 1).

- csharp-server, csharp-wasm-published: the C# core, from f593e47f (main before #501 removed it), in a
  worktree of its own. WebAssembly is a published client served by tools/serve-published.mjs.
- script-blazor-server, script-blazor-wasm-published: Blazor's components over the Script Core, from this
  branch, served the same way. CoreGrid hands its rows as `Rows`, the grid's in-memory source: a pushed
  Window is a new list, which is a new source.
- script-react: the Script Core under React (Bench.React), the grid pages only.

Each figure is the median over 5 rounds; "dom" is ms from the input until the change landed in the DOM,
"frame" until the animation frame after it; a frame p95 is over the 60 frames of a sustained phase, and its
lag is from the last input until that input is painted. Bytes are the circuit's connection that moved most,
after per-message compression; a call larger than 16 KB crosses as a stream, which this meter may not see
(the sheet's 78 bytes an edit). No phase failed, and no page logged an error, a warning or an exception.

The driver types a digit as the browser does, a keydown and then beforeinput and input on the field holding
the keyboard, since the Script Core takes typed text from those (ADR-0080). The C# core's two runs used the
driver as it was, which typed by the keydown alone; with the new driver the C# core's editor would take each
digit twice. The sheet's figures of the two cores are therefore read across that difference: the time the
browser takes to dispatch two events more, a few microseconds a digit.

What is slower (ADR-0350 section 15: said here and in the Change Notes, and fixed or accepted with the user):

1. The grid on Blazor Server, a push or a tick: about 28.6 KB on the circuit for every change, whatever its
   size (the C# core: 0.2 KB for one row, 13.6 KB for every painted row), and 8 to 20 ms where the C# core
   took 2 to 14. A new Rows list is a new source, and the bridge sends the rows around the painted ones
   again (ADR-0350 section 7's slice, "a few screens either side").
2. The grid on WebAssembly, a push or a tick: 21 to 27 ms over 1,000 and 10,000 rows (the C# core: 3 to 8),
   60 to 74 ms over 100,000 (18 to 31), and a tick every frame drops frames (p95 29 to 86 ms against 17 to
   39). The same slice, written as JSON by the .NET interpreter.
   Fixed on this branch for 1 and 2 (ADR-0350 section 15's note of 2026-10-30): a row the browser holds, the same
   instance under the same columns and Row Key reader, crosses as its id and what it paints, and a new Rows list
   reading the same columns no longer renumbers them. Measured again the same way (rows-and-batches/): a push of
   one row or a tick crosses 0.6 to 5 KB on Server (the C# core: 0.2 to 12.4) in 5 to 7 ms over 1,000 and 10,000
   rows (2 to 7) and 14 to 16 ms over 100,000 (10 to 12); on WebAssembly 7 to 14 ms over 1,000 and 10,000 rows (3 to
   8), a tick every frame keeping every frame there (p95 17 to 24 ms), and 45 to 58 ms over 100,000 (18 to 31).
   Still slower: a Window of all new rows (11 to 75 ms, as before), and 100,000 rows on WebAssembly, where every
   push is a new Rows list and so a new in-memory source over every row, built by the .NET interpreter.
3. Mounting the grid over 100,000 rows: 28 ms on Server (16), 77 to 80 ms on WebAssembly (22 to 25).
4. The sheet, an edit: A1, which 20,000 cells read, 147 ms on Server (103) and 1,074 ms on WebAssembly
   (641); L1, which nothing reads, 34 ms on Server (13) and 966 ms on WebAssembly (99), ten times slower.
   CoreSheet binds `Document`, so after every edit the browser hands .NET the whole document as JSON and
   .NET parses it (`SheetDocument.FromJson`, ExSheet.cs's "workbookChanged"): a CPU profile of one L1
   edit on WebAssembly spends about 700 ms in the .NET interpreter.
   Fixed on this branch (ADR-0370 section 1's note of 2026-10-30): a raised document now crosses as the
   cells that changed, and .NET builds it from the one before. Measured again the same way
   (sheet-changes/): A1 127 ms on Server (103) and 129 ms on WebAssembly (641, now five times faster); L1
   19 ms on Server (13) and 24 ms on WebAssembly (99, four times faster). What is left is the browser's:
   the Script Core's recalculation and paint, the same on both hosts.
5. The pivot: one trade amended, 63 ms and 63.5 KB on Server (4 ms, 2.6 KB) and 85 ms on WebAssembly (15);
   the columns swapped, 62 ms on Server (15), the same on WebAssembly (88 against 87). Not profiled: the
   bytes say each question's Leaf Aggregates cross in full.
   Fixed on this branch in part (ADR-0370 section 3's note of 2026-10-30): the bundled source's Change Batch crosses
   as the records it removed and added, which the browser folds into the answer it holds. One trade amended now
   crosses 152 bytes on Server (2.6 KB) and takes 63 ms on WebAssembly (85 before, 15 for the C# core); it still
   takes 60 ms on Server, where the C# core took 4. A CPU profile of five amendments on Server puts about 50 ms
   of each in ex-pivot's own script (addLeaf, merge, read: the engine laying the report out again from every
   leaf), and the circuit's part at under 10 ms. What is left is the Script Core's pivot engine, the same
   under React, and not the adapter's. Swapping the columns asks a new question, whose answer crosses
   in full as before.

What is faster, or the same:

- Keys: 40 arrows in one task, 4.6 ms on Server (9.5, and 0.4 KB against 9 KB) and 4.7 ms on WebAssembly
  (73, fifteen times faster); an arrow a frame keeps every frame on both.
- Scrolling: every frame kept on every arm; a slow scroll paints 2 ms after its input where the C# core
  painted in 0.4.
- Template cells: no measurable cost on any arm (template against grid).
- React, the Script Core with no .NET beside it: the fastest arm, 1.6 to 4.7 ms a push or a tick over
  1,000 and 10,000 rows, and 13 to 15 ms over 100,000, the C# core on Server's figure.
