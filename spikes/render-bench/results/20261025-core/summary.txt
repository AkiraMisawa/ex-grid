Where and how: 2026-10-25, a 4-core Linux container, headless Chromium 153 (Playwright's build, no
GPU) at 1400x1000; the 1-minute load average was 2.5 as the Server run began (the build had just
ended) and under 0.8 from then on. Bench.Server (5491) and Bench.Host serving Bench.Client
without AOT (5492), both built in Release and run with `dotnet run -c Release --no-build`, on loopback
with no added latency; the hosts measured one after the other, never at once. `main` at 5e3eecb.
Headless software rendering: read the figures against each other, and against the Script Core's taken
on the same machine, not as what a user's machine shows.

Reading, for the Script Core to be measured against:

- A Window on Blazor Server costs what its painted rows cost, whatever its size. Pushing a new
  Window of 1,000, 10,000 or 100,000 rows puts the same ~13.6 KB on the wire (every painted row
  new) and takes 7 to 15 ms; one row new is ~0.9 KB. The grid's pass over the Window runs on the
  server and never crosses. Under the Script Core the Window crosses into the browser (ADR-0350
  section 15, the first risk): this is the line it is compared with, at 100,000 rows above all.
- On WebAssembly the same pass is paid in the browser, in proportion to the Window: a new instance
  of 100,000 rows takes 60 to 85 ms however few rows changed (push one, tick 1), against 6 ms at
  1,000. A live source handing over a 100,000-row Window every frame runs at 80 to 115 ms a frame
  (p95). The Script Core on WebAssembly pays a crossing instead of this pass.
- Template cells cost nothing measurable here on the C# core: /core/template is within noise of
  /core/grid on both hosts, a component cell included. Under the Script Core a component in a
  template cell is a component root of its own (the second risk); this is its baseline.
- ExSheet on WebAssembly: an edit that recalculates 20,000 cells takes 3.3 s until the screen shows
  it, against 130 ms on the circuit, and an edit of a cell nothing reads still takes 370 ms against
  15 ms. Where that time goes on WebAssembly (the engine on the interpreter, the grid, or the Sheet
  Document handed back after each edit) was not run down. On the circuit an edit sends 5 to 16 KB. The Script Core leaves
  the engine where it is and adds the crossing of its Values (the third risk).
- ExPivot: a Change Batch of one trade redraws in 4 ms on the circuit (2.6 KB) and 79 ms on
  WebAssembly; swapping the columns, 17 ms and 400 ms.
- Keys and scroll: 40 arrows in one task land in 11 ms on the circuit (9 KB) and 157 ms on
  WebAssembly; an arrow or a 37 px scroll per frame keeps every host at its frame, the Sheet and the
  pivot on WebAssembly excepted (p95 56 and 67 ms while scrolling). A fling of 50 rows per frame
  paints Placeholder rows and fills them about 160 ms after it stops (ADR-0004), which is the grid's
  design, not its lag; the Sheet and the pivot on WebAssembly take 330 and 200 ms.
